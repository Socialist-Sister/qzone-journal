## 审查范围与已修复问题

| 范围 | 发现的问题 | 修复后的行为 |
| --- | --- | --- |
| 视频与图片下载 | 整个媒体累积到 Buffer，再复制写入；并发视频提高内存峰值 | 分块写入独占临时文件，等待磁盘写入后再取下一块，校验结束后原子提交 |
| 下载质量 | 截断响应可被保存；失败临时文件可能残留 | 校验声明长度、实际长度和大小上限，失败清理临时文件并保留已有完整文件 |
| 下载兼容 | MIME、安全校验和磁盘失败也会重复请求 | 仅对明确的临时网络阻断/部分 HTTP 错误使用兼容请求，不重复磁盘写入错误 |
| 下载进度 | 单条大视频下载时页面长时间没有更新 | 显示已接收并写入的本轮媒体字节数，节流更新进度 |
| 增量备份 | 下载后的 MIME 改变指纹，导致不变说说反复更新；外链不参与指纹 | 指纹比较内容语义、媒体来源及外链，忽略下载结果；统一空计数 |
| 增量补下载 | 已保存原视频但缺少封面时被跳过；较早缺失媒体可能被提前停止的增量扫描遗漏 | 分别检查原视频/封面，索引记录待补媒体状态，需要补媒体时继续扫描 |
| 视频解析 | 封面不同 URL 别名进入图片网格；重复字段可能丢弃原视频地址 | 跨字段排除封面/缩略图，合并同一视频的可播放来源与封面 |
| 外部视频 | 带 QQ 缩略图的 B 站链接卡片可能被识别为原生视频 | 外部链接仍按外链归档，不把缩略图伪装为原生视频 |
| 点赞详情 | 后续分页失败丢弃已取得名单；结束状态不明确 | 保存已取得的数据与此前名单，以 partial 状态结束，后续备份继续补充 |
| 采集取消 | 分页等待积累 abort 监听；一个下载失败后其它并发写入尚未收尾 | 等待完成后移除监听，失败停止分配新任务，全部下载收尾后再处理恢复点 |
| 任务互斥 | 异步准备阶段尚未登记采集/导出任务 | 在首个异步操作前占用锁，采集会话清理结束后释放 |
| 本地读取 | 被篡改的媒体缓存或索引内部文件名可能越界 | 复验缓存路径、真实路径、文件大小；异常索引从本地记录重建 |
| 维护修复 | 修复记录前没有脏标记；每个媒体反复扫描所有异常 | 修改前保留脏标记，异常按条目分组；识别缺失、空文件与大小不符媒体 |
| 档案搜索 | 旧分页结果可能追加到新查询；服务端评论命中被前端再次过滤 | 请求按查询代次隔离，实时档案采用服务端匹配结果 |
| 视频前端 | 切换条目可能复用旧播放器；只有封面仍显示播放图标；缺少错误说明 | 按条目重挂载、延迟读取，封面去除播放图标，增加明确的失败/补备份说明 |
| 导出 | UTC 与本地日期按字符串比较造成跨日漏导；普通图片误触发“有视频封面”说明 | 按真实时间筛选，按实际导出的封面数量说明；主动省略媒体时说明原因 |
| 搜索导出 | 当前筛选导出不包含只命中评论的记录 | 档案筛选和导出均支持评论文本匹配 |
| 账号与时间 | 翻页反复写同一份账号资料；首次失败可能显示成功备份时间 | 资料实际变化时才写入；没有完成时间时明确显示尚未完成 |
| 诊断 | 媒体失败诊断包含原始下载 URL | 仅保留媒体类型、原因类别和 HTTP 状态 |
| 发行 | 版本测试写死旧值；SHA 清单混入保留的旧安装包 | 版本断言跟随项目版本，发行清单只选择本版本资产与匹配的更新元数据 |

## 性能证据

`scripts/benchmark-media.cjs` 使用本机生成的相同 **64 MiB** 内容，在独立 Node 进程对比缓冲/流式写入，不访问 QQ。

| 方式 | 采样 ArrayBuffer 峰值 | 本地处理耗时 |
| --- | ---: | ---: |
| 缓冲后写入 | 128.03 MiB | 71 ms |
| 流式写入 | 58.08 MiB | 66 ms |

本次采样峰值约降低 55%。这是合成媒体的 ArrayBuffer 内存对照，不是总进程内存，也不代表真实 QQ 网络提速。垃圾回收、存储设备和其它进程会影响结果。测试命令：

```powershell
node --expose-gc scripts/benchmark-media.cjs buffered
node --expose-gc scripts/benchmark-media.cjs streamed
```

1 万条记录、5 万个媒体引用的索引、统计和分页压力测试通过。日志中的耗时包含生成 1 万个 JSON 文件，不能当作一次页面查询耗时。

## 尚未证明或后续仍需处理

1. 真实 QQ 上传视频接口、重定向/Referer、离线 MP4 播放、重复备份和登录失效恢复仍须真实账号验收，不应去除 Alpha。
2. 真实 Windows 10/11 干净系统安装、升级回滚、WPS 与可信 Windows 代码签名仍需人工验证。
3. 多年大档案的导出仍在主进程聚合导出模型与媒体；本轮限制了记录读取并发，但没有实现整个 HTML/DOCX/PDF 的流式生成。超大导出仍有内存压力。
4. 归档完整性检查以路径、JSON、存在性和长度为主，不能识别所有大小相同的媒体内容损坏。
5. 图片/视频仍依赖 QQ 返回可读取地址，不能保证找回接口未返回或已失效的原文件；完整相册、独立日志和完整视频库未扩展。

实现参考：[Node FileHandle API](https://nodejs.org/api/fs.html#class-filehandle)、[Electron net API](https://www.electronjs.org/docs/latest/api/net)。本报告的修复与测试结论来自本地代码、测试和截图。
